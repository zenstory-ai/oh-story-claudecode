# Agent Note: 长篇拆文主会话不中转内容——子代理自读原文、自写批次输入，聚合改用 digest 取料

Status: implemented
Date: 2026-09-24
Related: [2026-09-23-long-analyze-runtime-takeover](2026-09-23-long-analyze-runtime-takeover.md)

## Problem

恢复逐章多情节点以后，每批输出变大。实测一本一百多章的书重拆：每批平均 1.3 万字符，其中逐章块约占七成、跨章观察约占三成，每章平均 16 个情节点。管道里有三处让主会话白白过手内容：

1. **原文转贴**：chapter-extractor 模板写着「调用方必须提供该块全部原文」。照字面执行，主会话要先把整批原文读进来，再写进派发 prompt。
2. **结果中转**：chapter-extractor 没有 Write 权限，整批结果只能作为返回消息交回主会话，主会话再把全文原样写成 `输入-{批次ID}.md` 才能提交。全书约 64 万字符要在主会话里收一遍，再按主会话模型的输出价写一遍，1M 上下文会反复触发压缩。
3. **聚合读整份缓存**：`material-decomposition.md` 前后说法矛盾。一处写「读已降维的跨章观察」，另一处写「Stage 3-5 的语料是完整批次结果」「主线程一次消费所有紧凑批次结果」。照后者执行，要把与逐章摘要重复的章节块全部再读一遍，全书放不进一次上下文。

另有几处契约空转：
- 输入清单里的「已确认别名」没有任何调用方提供；
- 情节点密度规则没有区分原文块和旧成果补摘要；
- #438 删掉旧黑名单后，长篇再没有「泛称不算人物」的规则，短篇拆文却还在引用那份已不存在的黑名单；
- story-setup 仍要求 chapter-extractor 保持只读；
- 批次间交接只写在文档里：chapter-extractor 要求调用方提供「上一批未闭合剧情点…」，但 plan/commit 不提供，派发步骤也没写，实际只能靠主会话中转全文后顺手摘抄；一并行就断，story-import 的提示却按并行写。

## Decision

- **派发只给路径**：批次 ID、输入类型、计划的 `source_files`（原文块是逐章 `source_locator`）、`chapter_chars`、输出文件路径、上一批缓存路径。chapter-extractor 自己按行号 Read 原文，自己 Grep 上一批缓存里的 `### 跨批状态`。
- **子代理自写输入文件**：
  - 模板 `tools` 增加 Write 与 Edit，仍禁 Bash；Edit 用于自查或被拒后只改出错的几行，不整份重写；最终回复只有一行 `BATCH_WRITTEN: 批次ID | 路径 | 各章情节点数`。
  - 主会话不 Read 这份文件，直接 `commit`；被拒时把错误码交回子代理，由它用 Edit 只改出错处。
  - 交接改为给子代理一个已提交批次的缓存路径，由它自己 Grep `### 跨批状态`。
- **派发方式分三档，Stage 1 后停下询问时由作者选**：
  - 串行：上一批提交再派下一批，交接给紧邻前一批；
  - 有限并行：每轮 3 批，同轮都读本轮开始前最近一个已提交批次的交接，整轮提交再派下一轮；
  - 不限批次顺序：同时在跑最多 12 个子代理（环境上限更低时以环境为准），在跑少于一半就补派到上限；补派用 `plan --next` 多取、跳过在跑批次号；遇限流、超时或报错上限减半；每批读本批起章之前最近的已提交批次的交接。
  - 作者没选、要求全量拆、多本书一起拆或由导入自动续跑时都按第 2 档，后三种不再询问；第 3 档只在作者明确选择时使用。交接批不紧邻本批时，子代理不假设中间章节已接上，另建剧情点 ID 交给 Stage 3 跨块合并。
  - 不论哪一档，`commit` 都由主会话逐个执行。
  - 子代理不可用时仍由主线程自己写，降级路径不变。
- **写入路径由内联 hook 限定**：
  - chapter-extractor 的 frontmatter 挂 PreToolUse(Write) hook，调 `story_hook_cli.js analysis-input-guard`。
  - 只放行项目内、所在拆文目录有 `chapter_index.csv` 或 `_progress.md` 的 `_analysis_cache/输入-{RAW|REUSE}-{起章}-{止章}.md`，其余一律 exit 2 阻断并说明原因。
  - 读不到 hook 输入时放行；node 缺席时 hook 命令本身失败，同样不阻断。这两种情况都由提交脚本对文件内容做完整校验兜底。
- **计划按需输出**：`plan --next N` 只输出前 N 批，`--next 0` 只看进度；两种都保留总数 `remaining_batches`，`summary_gaps` 压成区间。全量计划每批约 540 字符，一本约 49 批的书单次约 2.7 万字符，按「每提交约 5 批确认一次」累计约 12–15 万字符，与聚合阶段读全书观察同一量级。逐批派发改用 `--next 1`，不带参数时输出不变。
- **聚合取料走 digest**：`manage_analysis_run.py digest` 是只读子命令，输出 Markdown，两种都可以用 `--chapters` 限定章节窗口。
  - `--part observations`：按章序汇总已提交批次缓存的跨章观察，只认进度表里已完成且缓存完整的批次；旧项目没有状态行时，退回扫描完整缓存。
  - `--part chapters`：从逐章摘要按标签抽字段；`--points brief|full` 给情节点简表（标题｜类型｜基调）或带白描的全文。
- **统一读法**：SKILL.md、pipeline-ops、material-decomposition、output-templates 改成同一种读法；散落情节兜底改为按窗口取情节点简表。
- **输出前机械自查**：生产实跑 15 批被提交脚本退回 3 次，全是模板写了、子代理偶尔漏写的格式——情节点行漏加粗短标题、章级字段漏「涉及人物」、某个情节点漏单独一行「主题标签｜基调」。chapter-extractor 的输出前检查新增第 10 条：写完先用 Grep（count 模式，只看数字）数情节点行、带标题的情节点行、标签行和十个章级字段，对不上就用 Edit 就地补齐，全部对上才回执。自查模式与提交脚本接受的格式由回归测试锁定。
- **契约配套**：
  - 「已确认别名」写进 `### 跨批状态`，由批次之间自己传递；agent 定义和主线程降级用的 output-templates 同步改。
  - 情节点「10–20、按字数」只适用于原文块；旧成果补摘要下限 1 个，按旧资料写到的事件拆，不凑数。
  - `涉及人物` 与 Stage 4 建档排除群体称呼、无名路人和泛称；短篇拆文改为自带完整的泛称清单。
- **周边口径**：
  - story-setup 的 Codex/Antigravity 部署规则把 chapter-extractor 移出只读 agent；
  - story-import 自动续跑时按「有限并行」档派发（每轮 3 批）；
  - Codex/OpenCode 适配层重新生成，两份适配检查的只读清单同步移除 chapter-extractor。
- **版本号本 PR 不动**：UPGRADING 与 CHANGELOG `[Unreleased]` 已写明，已部署项目需要重跑 story-setup，发布时提升 `agents_version`。

## Alternatives considered

- **保持子代理只读，主会话照旧转写**：
  - 最强理由：只读子代理最安全，不可能写坏拆文目录。
  - 不采用：转写没有任何加工价值，却占掉主会话大半上下文，还要按最贵的模型把内容重新生成一遍。
- **只给 Write、修正时整份重写**：
  - 最强理由：权限面最小，子代理改不动已写的内容，只能从头覆盖。
  - 不采用：每次修正都要把一整批（约 1.3 万字）重新输出一遍，而实跑中的退回全是漏一两行格式；Edit 受同一个守卫限定路径，只能改它自己的输入文件，风险不增加。
- **只靠模板指令约束写入，不加 hook**：
  - 最强理由：不碰 hook 基础设施，改动最少，而且提交脚本会拒收格式不对的文件。
  - 不采用：提交校验只看输入文件本身。子代理如果误把内容写进 `章节/第N章_摘要.md` 或别的文件，提交脚本察觉不到，会静默改坏已有成果。
- **把守卫放进各端共享的 `story_hook_core.js`**：
  - 最强理由：规则只写一份，各端同一实现。
  - 不采用：只有 Claude Code 支持挂在单个 agent 上的内联 hook，其他端用不上；共享核要求四份副本逐字节一致，为 Claude 独有的挂载点改四份不值得。放在 Claude 侧桥接文件 `story_hook_cli.js` 就够了。
- **写成纯 bash 守卫脚本**：
  - 最强理由：没有 node 的运行时也能拦住。
  - 不采用：bash 解析 hook 输入的 JSON 很脆弱；缺 node 时 fail-open 的后果有限，提交校验和模板指令仍在。
- **Stage 3–5 直接读逐章摘要、不读缓存**：
  - 最强理由：少一个子命令。
  - 不采用：跨章观察只存在于缓存里；逐章 Read 要打开一百多个文件，过手量也不比读缓存省。
- **只允许串行**：
  - 最强理由：交接最完整，剧情点 ID、未闭合状态和别名逐批接续，Stage 3 最省事。
  - 不采用为唯一方式：3 章一批时一本书要几十批，串行的墙钟时间太长；#438 之前的独立提取本来就靠 Stage 3 跨块合并兜底，并行不会让数据失效，只是边界接续更依赖事后合并。取舍交给作者。
- **默认第 3 档（不限批次顺序）**：
  - 最强理由：最快，整本书的墙钟时间最短。
  - 不采用：生产实跑只验证了串行和每轮 3 批，第 3 档没有实跑过；它开头一轮十几批都拿不到交接，别名和剧情点接续全压给 Stage 3/4 事后合并。默认值取验证过、接续最多滞后一轮的第 2 档，要更快的作者主动选第 3 档。
- **不设并发上限**：
  - 最强理由：最快。
  - 不采用：宿主和账号都有并发与限流上限，一次派几十个子代理会触发限流、整批失败重跑，反而更慢更贵；因此同时在跑封顶 12 个、不超过环境上限，低于一半才补派，出错即减半。

## Consequences

收益：
- 主会话 token 约省 75%，按 Opus 计费约省 86%（$20 → $2.8）。以一本约 49 批的书、派发只给行号的口径算，Stage 2 每批的固定开销用生产实跑实测值，中转和聚合量粗按 1 字 ≈ 1 token：
  - 改造前：约 159 万读入（每批固定开销约 5.8 千 × 49 ≈ 28 万、结果中转约 67 万、聚合整读缓存约 64 万），约 70 万写出（重写输入文件为主）。
  - 改造后：约 54 万读入（固定开销 28 万、聚合 digest 取料约 26 万），约 3 万写出（派发说明）。
  - 实测的每批固定开销主要是：子代理回执外的系统包装约 1.3 千字、派发说明约 630 字、提交结果约 410 字、`plan --next` 约 800 字，加上主会话自己的推理和工具调用；这部分改造前后都有。
- 实跑一个续拆会话：从 5.75 万 token 起步，做完约 13 批后 13.3 万，没有触发压缩，整本书可以在一个会话里跑完。
- 聚合阶段按 66 章实测：跨章观察 7.8 万字符，情节点简表和四个常用字段各约 1.9 万字符，合计约为整份缓存 28.8 万字符的四成，而且可以按窗口分次取。

代价：
- chapter-extractor 有了写权限。在 Claude Code 上由内联 hook 限定路径；Codex/OpenCode/Antigravity 没有这个挂载点，只能靠 agent 指令和提交校验约束。
- 已部署项目必须重跑 story-setup 才能拿到可写的 extractor 和守卫，发布时要提升 `agents_version`。
- 主会话看不到批次内容，抽查质量要另外 Read 摘要。
- 并行两档的边界接续变弱，Stage 3 跨块合并与 Stage 4 别名归并的工作量随之增加；默认档（作者没选即有限并行）在速度和接续之间折中，需要最稳的作者主动选串行，要最快的主动选第 3 档。
