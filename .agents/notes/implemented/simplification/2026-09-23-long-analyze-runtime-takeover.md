# Agent Note: 拆文运行时接手收口——恢复情节点、写回最终状态、删掉用不上的状态分支

Status: implemented
Date: 2026-09-23
Issue: PR #386 / #438（维护者接手）
Related: [2026-09-22-long-analyze-single-state-runtime](../architecture/2026-09-22-long-analyze-single-state-runtime.md)

## Problem

单状态三脚本运行时（见 Related）在接手复测中暴露四个合并阻断：

1. 逐章摘要的情节点从 main 的每章 10–40 条变成结构上只产一条 `P1`，连带丢掉地点、
   物品、时间、逐节拍基调与原文引用。情节点是长篇链路的基础数据：对标挑章按情节点数
   平票、结构关键点按「类型=转折点」情节点定锚、导入按情节点分布反推情绪弧线与伏笔。
2. 运行时从不写 `最终状态`，而会话 hooks 只认这个字段，新管道拆完的书每次开会话都被
   报成「未完成拆文」。
3. 原文改动后 `plan` 排出重读批次，`commit` 却因「已有摘要不覆盖」跳过全部写入，
   失效信号随之清空，看起来像刷新成功。
4. 章节身份守卫把本次 Stage 1 按索引写的黄金三章也当旧摘要：序章开头的新书写完黄金
   三章后 `plan` 永久阻塞。

同时运行时里有几块复杂度服务的场景基本不存在：显式重拆（`reanalyze` + `request_id`）
重读全书却不覆盖任何摘要；`migrate-legacy` 与六脚本进度识别服务一个从未发布的版本；
`v2/章节卡` 家族是作者独立项目的格式，main 从未产出过；原文局部修改的精确失效追踪
（`chapter_index.previous.csv`、历史索引比对、stale 投影）为「拆文原文被改」这种罕见
情况维护了一整条分支。

## Decision

- **恢复多情节点**：模型输出改为章级紧凑字段 + `**情节点**：` 下的 `P1..Pn` 序列，
  格式沿用 main（类型 | 白描 | 涉及 | 地点 | 物品 | 时间，可选引用行，每点一行
  `主题标签X | 基调：Y`）。原文块每章 10–20 个、长章最多 30 个，`commit` 机械校验
  10–30，越界整批拒收；由黄金三章补投影的旧成果块至少 1 个。类型/主题/基调逐点映射到
  枚举，映射改为「精确 → 别名 → 前缀」，不再用子串（`不紧张` 不再落成 `紧张`）。
  输出量随之变大，原文块上限从 10 章降到 5 章，25,000 字符上限不变。
- **受管区写 `最终状态`**：有阶段记录后，六个阶段都完成（或带错完成）写 `completed` /
  `completed_with_errors`，否则 `pending`；hooks 的 `analysis_incomplete` 直接可读。只做
  增强的旧项目没有阶段记录，沿用原有的 `最终状态`，不写第二个。
  Stage 1 后暂停不再单独写 `paused_after_stage1`，统一为 `pending`。
- **已有摘要永不覆盖，不做刷新**：原文改动只让覆盖它的批次缓存失效并在下次计划里重读
  该批，`commit` 在 `kept_existing_summary_chapters` 里如实列出保留的章。要刷新某章就
  删掉它的摘要再续跑；缓存已是新原文的就直接从缓存补回。
- **身份守卫只看 `upstream_summary`**：黄金三章与运行时投影都是按索引写的，不参与判定；
  `build_chapter_index.py` 的旧摘要冲突检查也只看 `_摘要.md`。书中番外导致的错位不做
  逐章身份比对。
- **删除**：`--intent reanalyze`、`--request-id`、受管区「本次请求」段、缓存里的
  `request_id/request_intent`；`migrate-legacy` 子命令与六脚本进度/缓存识别；
  `v2/章节卡` 紧凑家族；`chapter_index.previous.csv`、历史索引比对与 stale 投影检测。
  整本重拆就换新目录。
- 恢复 chapter-extractor 三端模板的「材料合法性与分析边界」（#143 的反拒答声明）。

## Alternatives considered

- **每章 1 个关键情节点 + 章级因果字段**：最强理由是批次输出短、10 章一批放得下；但三处
  下游按节拍序列取数，只留 1 条等于让它们整体退化，且这一改动在两轮评审里都没被讨论过。
- **维持 main 的 10–40**：与 main 完全一致；但 5 章一批时上限 40 让单次输出过长，按
  维护者意见上限收到 30、常规 10–20。
- **按投影标记四态刷新摘要**（缺失写入、hash 相符跳过、hash 失效留档后覆盖、无标记
  永不覆盖）：能自动跟上原文修改；但拆文原文很少被改，为此要新增留档路径与覆盖规则，
  不值得。
- **逐章身份比对守卫**：能拦住书中番外造成的错位；但序章/番外本身少见，逐章比对要引入
  标题归一与身份映射，放弃。
- **保留 `reanalyze`**：显式重拆有入口更友好；但在「已有摘要不覆盖」的前提下它只会重读
  全书、更新缓存，产物不变，入口本身有误导性。

## Consequences

收益：情节点契约回到 main，下游三处消费不再退化；hooks 能正确识别拆完的书；序章开头的
新书不再卡死；`manage_analysis_run.py` 1074→928 行、`inspect_existing_assets.py`
631→490 行、`build_chapter_index.py` 445→428 行，状态分支显著减少。

代价：原文局部修改后摘要不会自动更新，需要手动删摘要；书中插入番外时旧摘要可能静默
错位一位；原文块 5 章一批使批次数约翻倍；六脚本试运行版与 `v2/章节卡` 格式的项目不再
被识别（二者都从未随 main 发布）。
