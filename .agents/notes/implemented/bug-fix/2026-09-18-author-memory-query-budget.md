# Agent Note: 作者记忆注入预算：从读时静默截断改为写时预警

Status: implemented
Date: 2026-09-18
PR: #429

## Problem

`query` 的输出被原样贴进写作 agent 的 prompt，`QUERY_MAX_BYTES = 2048` 是它在
prompt 里的注意力预算（#368 的设计，不该放大）。但预算只在读取端执行：条目攒多
之后，按任务组合查询会静默截断，作者 `record` 拿到回执以为记住了，实际那条永远
进不了 prompt，且无任何征兆。老的 `omitted > 0` 提示语义（「收窄 kind 重查」）在
这种场景下会误导——条目是被预算挤掉的，不是筛选没命中。

## Decision

写入永不因注入预算失败，但必须**提前预警**，并让「被丢掉的是什么」可预测、可核对：

1. `record` / `commit` 返回 `warnings`：按 `references/author-memory.md` 映射表的
   四类任务组合估算最坏查询情形（全局条目＋各 scope 维度上最重的单一切片），装不
   下的组合点名将被略过的条目**及其断言首句**。写入本身照常成功。
2. 估算与真实查询是同一把尺：切片按 `casefold` 归并（与 `same_scope_value` 同口径），
   切片轻重按 `compact_bytes + 2`（算上 JSON 数组的分隔符）。两处口径任缺其一都会
   产生假阴性——回执说没事、随后的 query 照样丢条目。
3. 装填排序是 **重要度 → 本书例外 → 最近更新 → 确认次数 → 编号**。重要度必须排在
   scope 之前：scope 在前会让任意数量的 `low` 本书琐事挤掉 `high` 的全局铁律。
4. 装不下的条目跳过而不中断（一条长的不挡后面的短条），漏下的 ID 按**候选优先级**
   排序报进 `omitted_ids`（封顶 20，`omitted` 保留真实总数）。按丢弃先后排会让收尾
   回吐的高优先级条目正好被封顶切掉。
5. 新建条目的 `assertion` 限 120 字节；**强化已有条目不受此限**，否则存量长断言再也
   无法被确认，作者重申老偏好只会派生一条重复条目，库反而更挤。
6. `query --kind` 改为必传，按映射表选类型。
7. `作者画像.md` 显示 `importance`——它是超编时的去留依据，而「整理作者记忆」以这份
   文件为唯一输入，不显示就无从判断该退役哪条。
8. 文档规定**一条偏好就是一条记录，例外和限定不许拆出去单列**。逐条丢弃 + 拆条会
   只丢掉例外，把「除非 X 否则不要 Y」变成送进正文的绝对禁令。

不变式由回归测试钉住：`assert_no_false_negatives`（固定种子随机库穷举「回执没提醒
⟹ 任何真实 query 都不漏条」）、`assert_slice_weight_counts_separators`、
`assert_omitted_ids_follow_priority`。

## Alternatives considered

**超限拒绝写入（本 PR 第一版，ef5b504，已被推翻）。** 最强的理由：它把「写得进去就
一定载得进 prompt」变成结构保证，作者永远不会拿到一张骗人的回执，比任何提醒都硬。
不采用的原因是它会死锁——`enforce_query_budgets(updated)` 对事务后状态无条件调用，
一个已超编的老库连纯 `forget` 都会被拒，作者无法逐条减量清理，只能手改 state。

**只在「事务让情况变差」时拒写。** 比较事务前后的漏项数，不增即放行；减量操作天然
通过，只挡把库推过线的新增。它能同时保住结构保证和可清理性，是三者中最好的形态。
本次没有采用，是因为它把一个咨询性的提醒变成硬失败，需要先让提醒制在真实工作区跑
一段时间、确认误报率（估算是最坏情形，天然偏保守）之后再收紧；留作后续。

**放大 QUERY_MAX_BYTES。** 最简单，且注入 4KB 在今天的上下文窗口里并不夸张。不采用
是因为 2048 是「低优先级偏好在 prompt 里占多少注意力」的判断，不是技术上限；放大它
等于让作者偏好去和本章设定、文风裁决抢注意力，#368 已经做过这个取舍。

**压缩注入信封（去掉 `kind`、扁平化 `scope`）。** 每条固定开销 100 字节、断言上限
才 120，压缩信封能把 2048 字节的容量从约 11 条提到约 16 条，且不牺牲任何表达。没有
在本次一并做，是因为它会改变 `compact_item` 的字段集——那是注入契约，值得单独一篇
笔记和单独一次评估。

## Consequences

- 作者在库超编前就会收到点名提醒，提醒里带断言首句而不只是 `APxxx` 编号。
- 超编时先丢的恒是重要度低的条目；作者标 `importance` 的动机因此变强，文档也明写了
  「不要一律 high」。这对已有把重要度一律填 `high` 的工作区没有帮助，只能靠整理时下调。
- 提醒是常驻的：断言约 50 字节时，库里十几条就会开始每次写入都带 `warnings`。这是有
  意的——它描述的是一个持续为真的状态，不是一次性事件。
- 估算是最坏情形（全局＋各维度最重切片），因此会对「自己这本书下其实不漏」的作者报警。
  宁可偏保守：假阳性只是多提醒一次，假阴性就是这个 PR 要修的那个 bug。
- 注入预算之外仍有 `PROFILE_MAX_BYTES = 12288` 这道硬上限（本机实测 84 条 active 后写入
  直接失败，远在注入预算开始咬人之后），它不在本次的提醒阶梯里，只在文档里点明了存在和处置方式。
- `query --kind` 必传是破坏性变更；`assertion` 上限收紧只影响新建条目。两项都要在发版
  时记进 CHANGELOG 的 `Changed`。
