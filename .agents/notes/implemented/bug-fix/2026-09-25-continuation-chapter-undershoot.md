# Agent Note: 续写章系统性写短——写手没有分组篇幅锚点

Status: implemented
Date: 2026-09-25
Related: [v0.8 瘦身](../../implemented/architecture/2026-09-24-v0-8-lean-writing-loop.md)、Discussion #447、#361

## Problem

长篇续写章首检普遍不到字数下限，作者每章都被问「收下还是重写」。开书第 1 章反而达标。

- 用户：Discussion #447（ZCode，新开书「除了第一章，后面的章节都没有完成」）、#361（章节字数差距大、token 白烧）。
- 基准（demo 书 mid-daily，日更 3 章，2026-09-25）：

  | 运行 | 前组占最终字数 | 每情节点平均字数 | 最终 / 目标 |
  |---|---|---|---|
  | Codex v0.8 第一轮（c5） | 82% / 69% / 70% | 281–349 | 0.98–1.06 |
  | Codex v0.8 发版候选 | 25% / 35% / 28% | 224–236 | 0.84–0.88 |
  | Claude Code v0.7.11 | 53% / 46% / 58% | 178–197 | 0.64–0.79 |
  | Claude Code v0.8 发版候选 | 39% / 39%（首章未走 checkpoint） | 140–210 | 0.58–0.88 |
  | Claude Code 开书第 1 章 | 64% | 308 | 1.03 |

两层原因，同一个缺口：

1. **分组**：Codex 候选把前组切得很小（前两三个情节点），checkpoint 算出的剩余区间很大，后组仍按自然密度写，补不回来。
2. **密度**：Claude 写手每点约 180 字，10 个情节点、2400 字目标需要每点约 240 字。

写手收到的篇幅信息只有整章目标，外加「按整章分量刻度使用、疏密自行分配、不拆逐点配额、不自测字数、短了也不据此重写、under 不补」。前组该写多长、每点大概多少笔墨，全凭模型语感；「不补、不重写」的措辞在写手侧还可能被读成「短一点也可以」。

约束（来自 #370 与更早的 #187）：不能回到整章写完再反复扩写/压缩；逐点配额写成下限会让写手顶满每点、系统性超长（demo 实测 +58%）；欠字不自动补写，防注水。

## Decision

Claude Code 上的写手（`narrative-writer`）固定用 `model: opus`；分组、checkpoint、欠字不补与超字只删一次的收口规则都不变。OpenCode 部署时的模型分档建议把写手放进高端档；Codex、OpenCode 不固定模型，Antigravity 本来就把两者都映射到 `pro`，不受影响。

写手层 A/B（2026-09-25）：以 v0.8.0 候选在 Claude Code 上那次日更的项目状态为底，删掉第 N 章及之后的正文，用主会话当时真实交给写手的 prompt 重写第 22–24 章，照真实流程先写前组 → `wordcount checkpoint` → 交回后组；每臂每章 1 次。

| 臂 | 最终 / 目标（22、23、24 章） | 平均 | 首检带内 | 每章成本 |
|---|---|---|---|---|
| a0 现行（Sonnet） | 0.88 / 0.63 / 0.63 | 0.71 | 1/3 | $1.26 |
| a1 前组给按情节点折算的区间 | 0.73 / 0.65 / 0.86 | 0.74 | 1/3 | $1.60 |
| a2 给每点平均笔墨刻度 | 0.77 / 0.77 / 0.65 | 0.73 | 0/3 | $1.24 |
| a3 写手侧删掉「短了不重写 / under 不补」 | 0.90 / 0.77 / 0.58 | 0.75 | 1/3 | $1.61 |
| a4 每组确定性量一次、低于下沿只补一次 | 0.82 / 0.77 / 0.86 | 0.82 | 1/3 | $2.29 |
| **a5 同一 prompt，写手换 Opus** | **1.05 / 1.11 / 1.04** | **1.07** | **3/3** | **$1.27** |

- 只改篇幅说明（a1–a3）无效：a1 明确告诉写手前组约 1040–1330 字，第 23 章仍只写了 637 字。写手不照数字写，也数不准。
- a5 对 a0 用异家族评委（GPT）核对：三章配对盲评（交换顺序两次一致才算）Opus 3 胜；严格判定「演成场景」10/10、9/10、10/10（Sonnet 9/10、9/10、10/10）；兑现全落地；越界新增第 23 章 2 条对 1 条，其余两章都是 0。评委理由集中在 Opus 用动作和生活细节写出情绪，Sonnet 更常直接总结。
- 分组层面的原因（Codex 前组切得过小）不在本次修复范围；Codex 不固定写手模型，由用户自己的模型决定。

## Alternatives considered

- **只改写手收到的篇幅说明（前组区间、每点刻度、删偏短暗示）**：最强理由是改动最小、不换模型、不影响额度。不采用：三种说法实测平均 0.73–0.75，与现行 0.71 无差别，写手不按数字写。
- **写手每组确定性量一次、低于下沿只补一次**：最强理由是不换模型，靠机器量字把「补」限定在已批准情节点里。不采用：平均只到 0.82、首检仍 1/3，每章成本近乎翻倍，且补写正是 #370 要避开的注水入口。
- **恢复逐点字数配额**：最强理由是最直接的篇幅锚点，写手照着写。不采用为首选：#187 实测配额写成下限会系统性超长 +58%，写成分配区间也需要主会话逐点估算、增加细纲字段，与 v0.8 精简方向相反；只在候选 1、2 都无效时再测。
- **欠字时自动续写补足**：最强理由是作者不用每章做选择。不采用：#370 正是为了避开整章写完再扩写的注水与反复改写；补写最容易加解释性心理活动与重复互动。
- **只调细纲的情节点数量**：最强理由是写手按点写，点多自然长。不采用为首选：点数是剧情设计问题，为字数加点会逼出注水情节；数据里点数相近时字数差异仍大（Codex 两轮都是 7–9 点，字数比 1.0 对 0.85）。

## Consequences

- 收益：Claude Code 上续写章首检带内率从 1/3 到 3/3，作者少做一次「收下还是重写」的选择，正文配对盲评也更好；每章成本基本持平。
- 代价：Opus 消耗订阅额度比 Sonnet 快，额度紧的作者会更早碰到限额。证据只有 demo 一本书、每臂 3 章，克制题材（虐文、世情）写手天然偏短，需要另行复测；若出现系统性超长，回看超字只删一次的收口是否够用。
