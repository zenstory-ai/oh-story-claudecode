# Agent Note: v0.8 瘦身——单章回路减负、概念收敛、AI 味改走可验证路线

Status: proposed

## Problem

用户对当前版本的四条主要诟病：token 消耗大、运行时间长、AI 味重、概念和机制过于复杂。四条同源：每修一次事故就加一条规则、一个检查或一个术语，很少删；热路径越积越厚，写手拿到的规则比故事素材还多。

### 1. token 与耗时：钱花在流程上，不在正文上

实测（e2e 真会话，Claude Code + 部署 hooks 与子 agent，demo《让你管账号，你高燃混剪炸全网》第 22–23 章前后；**写手模型为 MiMo v2.6-pro，不是 Claude，绝对值只作量级参考**）：

| 指标 | 实测 |
|---|---|
| 每章墙钟 | 49–67 分钟（日更 2 章约 49 分钟，含补两章细纲；单章 51–67 分钟） |
| 每章累计输入 | 5–8M token，88–96% 为缓存读 |
| 主会话上下文 | 中位 80–118K，峰值 155–162K；每次运行 10–15 分钟内必然触发一次自动压缩 |
| 主会话回合 | 串行 15–18 轮；子 agent 3 次 + 1–2 次续写；脚本 12–14 次 |
| 上下文 : 正文 | 每章加载约 20 万 token 上下文，产出约 2K token 正文，约 100 : 1 |

静态核算（按文档规定的必读项逐一计数，中文约 1.2 字/token）：

| 角色 | 规则 | 数据 | 每章加载 |
|---|---|---|---|
| 主会话 | ~41K（会话内一次）+ harness ~5K | ~32K/章 | 首章 ~78K，同批第 3 章 ~140K |
| narrative-writer 写作 | ~34K | ~16K | ~50K |
| narrative-writer 去味审查 | ~39K | ~4K | ~43K |
| consistency-checker | ~5K | 29–58K，随书增长 | 34–63K |

主要成本来源：

- **写手和审查每次都从头读一整套规则。** `writing-craft`、`banned-words`、`style-resolution` 在同一章被读 2–3 次。narrative-writer 模板的 `skills: [story-deslop]` 把整份 deslop SKILL.md（~5.8K）预加载进每次调用，任何预算都不计它。
- **追踪提交占输入 token 的 16–24%。** 它在上下文最胖时执行，又频繁被字节上限打回：delta >3072、result >480、summary >360，每章重试 2–3 轮。
- **consistency-checker 是最慢的单步。** 一次前台 15 分钟，另一次后台 13 分钟。它读全部细纲、全部角色卡、全部设定，读量随章数线性增长。
- **去味审查每次调用 8–9.5 分钟。** 有一次整个调用只为处理一条 advisory。
- **写手单次调用有 45–85K 字符隐藏思考**，产出 2–3K 字正文；一次 Write 前静默 4–6 分钟很常见。
- **热路径预算全部顶格**：长篇日更主会话 45,450/45,500，正文 agent 基础规则 42,625/42,700，direct/solo 88,832/88,900。author-memory、tracking-transaction、reader-contract、emotional-arc-design、dialogue-mastery 以及 agent 预加载的 skill 实际每章都读，却不在任何预算路径里。
- **历史趋势**：v0.6.0 → v0.6.22 热路径膨胀 3–4 倍（SKILL.md 17K → 64K、narrative-writer 8K → 35K、anti-ai-writing 15K → 35K），之后靠外移 references 控制单文件字数，但每章实际加载总量没有降。#332（日更固定加载 ~90KB）当时以「无 token/延迟证据」关闭，现在有了。

### 2. 概念与机制：长篇流程约 75 个具名概念

多数是事故补丁，高度重叠：

- **4 套「三档」**：开书 A/B/C 创作授权、写手一/二/三档、主会话 ①收编/②修复/③提请、写手自由区。它们问的是同一个问题：下一章需不需要知道它存在过。
- **读者契约 11 个术语**：契约安全/需补强/契约破坏、期待债、终局储备/底牌/台阶、主推线/战果、因果权/结算权、关键节点四问、期待所有权、换书债、透支两问、七类状态。全部来自 #237，各自出现在 5–15 个文件，没有一个由脚本强制。
- **5 套排纲安全检查**：七检、安全审查、供给自查、建纲追加、批次级复检。为了把排纲底稿和写作输入分开，又派生出 `--stage` 和作用域声明。
- **去 AI 味在 3 处各跑一遍**：长篇写后收尾、story-deslop、story-review，共用 4 个被拷贝到 4 个 skill 的脚本。叠加 7 Gate、三遍法、最毒句式速查、轻/中/重度、反套话四问、写法抽查四项等并列层级。
- **5 套严重度口径**：S1–S4、blocking/advisory、契约三级、轻/中/重、漂移三级。
- **规模数字**：写作期脚本 58 份，按唯一名只有 35 个，冗余拷贝 1.76MB；hooks 约 2,250 行；7 种 agent；一个书项目约 30 类产物；追踪 JSON 约 70 个键。用户面有 13 个 skill，新手真正需要 4 个。

### 3. AI 味：规则堆不动，已有实验说明方向

- **写手拿到的规则比素材多**：约 34K token 规则，对约 16K 故事材料。规则多是「禁止 X」清单，再加写后扫描、删改。
- **tell 子项目 r1–r6**（`~/workspace/tell/rounds/`，写手为 GPT-5.6）：
  - 泛泛一句「别有 AI 味」、只换作者角色、给整章范文，均无效。
  - 8 条可数约束能推动可数项：台词正式名词 2.5 → 0.39/篇，感叹号为零 7 → 0 篇，对话占比 0.33 → 0.26，情节点全落地 11 → 16/18，没有质量代价。
  - 检测器数值反馈改稿能推动分布项（「的」、口语词、感叹号），代价是刷指标：塞词、字数膨胀 1.25 倍、卡顿上升。
  - 盲测识别率始终 18/18。
- **反平推「具体度」预注册复现未确证**：+1.21，p=0.283，章间差异大于平均效应。
- **方法教训**：Claude 评委 + 并排对比 + Likert 会把 +1.2 的效应放大成 +6～+9。PR #228「热路径去重被盲评否决」恰好用的是这套方法（Opus 三评委、每臂 4 份、Likert），所以「删规则会退步」和「删规则无损」**目前都没有被可靠地证明**。
- **写手模型选择**：narrative-writer 默认 `model: sonnet`，story-architect 是 `opus`。token 大头在流程，写正文这一步反而没用最强模型。

## Proposal

原则：**单章回路里只留「写」；机械的事交给一次脚本调用；检查按批做或出了问题才做；每项删减都过同一套基准。**

### 0. 先建基准（所有后续改动的门槛）

- 把 e2e 驱动固化进仓库（`scripts/` 下的 bench runner，只提交工具，产物不入 git）。当前驱动只存在于一个会话的临时 scratchpad，随时可能丢失。
- **固定语料**：3 本不同题材的书 × 连续 3 章，写手分别用 Claude 与 GPT 跑。
- **效率指标**：每章墙钟、累计输入/输出 token、主会话回合数、子 agent 调用数、压缩次数、第一稿落在字数带内的比例（按模型分列）。
- **质量指标**：
  - tell 检测器的人类区间偏离项；
  - 情节点覆盖与串味（可数）；
  - 换模型家族评委的单份盲评。
  - 质量结论一律走预注册协议（冻结协议与分析脚本、换架构评委、单份盲评、可数主指标），沿用 `.ab-chronotope/preregistered/` 的做法。
- **先跑出 v0.7.11 基线**，之后每个改动前后都跑。

### 1. 单章回路减负（token 与耗时的主力）

| 改动 | 预期 |
|---|---|
| **写手不再自己读 references**。`build_writer_prompt.py` 注入一份 ≤5K 的写作要点（正向、可数的约束 + 本书文风原文片段 + 本章相关的题材卡条目）；删除 narrative-writer 模板里的 `skills: [story-deslop]` 预加载 | 写作调用规则从 ~34K 降到 ~5K |
| **新增 `storyctl chapter finish`**：一次调用依次跑 normalize-punctuation、check-ai-patterns、check-outline-copy、check-degeneration、`chapter check`，返回一份合并的短报告；追踪事务超限时由脚本给出能直接照改的精确提示，逐章记录类字段可自动截断 | 12–14 次脚本调用 + 2–3 轮提交重试 → 1–2 次 |
| **consistency-checker 按需**：写手申报了二档新增物、或检测到跨章事实时，才对相关实体跑；否则每批结束跑一次。读取范围改为按实体定点读，不再全读 | 省掉每章 13–15 分钟的最慢单步，读量不再随书增长 |
| **去味审查按需**：只在检测器报出 blocking 时调用，做一次定点改写；advisory 汇入批末报告 | 多数章省一次 8–9 分钟的调用 |
| **主会话单章操作手册 ≤8K**：`workflow-chapter` 只留编排步骤，编排交给脚本，规则进写手要点或脚本 | 3 章一批内不再触发自动压缩 |
| **模型分工**：写手默认用最强模型，checker、explorer 这类机械角色用便宜模型；在基准上验证 | 把流程省下的 token 花在正文上 |

**建议目标**（以 Claude 写手为准，基线跑出后校准）：每章 ≤15 分钟、≤1.5M 累计输入、主会话 ≤6 轮、子 agent 调用 ≤2 次、3 章一批零压缩。

**明确保留，不在瘦身范围内：**

- **前后两组分段写作 + 中途一次字数 checkpoint。** 它是 #370 实验后定下的默认（`5b4a7e3` 又把「一次成文」退回只在作者显式选择时才用）。它掐掉的是旧流程整章写完再反复扩写、压缩的死循环：9/9 章落在带内，每章恰好一次 checkpoint。成本只有一次脚本调用加一次续写往返，是回路里性价比最低的删减对象。
- **非对称收口**：欠字不补、超字只净删一次、仍带外由作者选。
- **hooks 的强制职责**：正文前置、写后毒句式兜底、欠账门。门禁放在 hook 而不是提示词里：低档模型会跳过提示词门禁，基准也必须部署 hooks。
- **`_tracking-state.json` 作为唯一结构化权威**，以及派生视图机制。

MiMo 在有 checkpoint 的情况下每章仍偏短，而 #370 的 GPT 实验 9/9 落在带内。偏短看来和写手模型有关，不是机制问题。基准按模型统计第一稿带内率；某个模型系统性偏短时，只对那个模型调整（例如调整目标换算），不动分段默认流程。

### 2. 概念收敛（降复杂度）

- **一张新增物表**：直接写 / 写了要报 / 先问作者。取代 A/B/C、一/二/三档、①②③ 和写手自由区，只在一个文件定义，其他地方只放指针。
- **读者契约压成 4 个问题**（主角有没有自己挣到结果；收益有没有被别人拿走；有没有提前烧掉后面的底牌；这章给读者留了什么期待）。只保留「终局底牌」这一个名词，其余术语退役。
- **排纲底稿移出卷纲**（例如 `大纲/排纲底稿/`）：`--stage` 与大部分作用域规则随之消失。七检、安全审查、供给自查、建纲追加、批次级复检合并为一个「排纲前自查」。
- **去 AI 味只留一条管线**：检测器 + 一次定点改写（见第 3 节）。story-deslop 和 story-review 调用同一步骤；三遍法、最毒句式速查、轻/中/重度、写法抽查不再作为独立层级。
- **一套严重度口径**：必须修 / 建议看 / 仅提示，贯穿 checker、review、检测器。
- **删掉只靠文字维持、且已被脚本覆盖的仪式**：
  - Constraint Lock：由 `chapter check` 与细纲契约覆盖；
  - 中途快照：每章提交后已有 `check`，日更模式本来就跳过它；
  - 内带：只保留用户带；
  - `gaps.*` 七路分支。
- **共享运行时只打一个包**：author memory、tracking、检测器、字数脚本作为一个 runtime payload 由 story-setup 部署，不再在 5 个 skill 各放一份拷贝。这会改写 [跨 skill 拷贝笔记](../../implemented/architecture/2026-05-07-cross-skill-copies-not-symlinks.md) 的前提，落地时另开一篇笔记并互链。
- **用户面**：README 和 `/story` 只主推 4 个 skill（story、story-setup、长篇或短篇写作、去味），其余标为进阶。

### 3. AI 味：在精简后的基座上做可证伪实验

1. **精简 A/B（兼作第 1 节的上线门槛）**：同一细纲，当前写手 prompt 对精简要点版 prompt。预注册，GPT 当评委，单份盲评，用可数指标，3 本书 × 多章。假设是质量不降或更好；**这个假设未经验证，不达标就不上**。
2. **写作要点只放正向、可数的约束**：r3 中起效的那几条（台词不念设定全称、对话占比、感叹号、主角有第二回合、每个情节点落地），替换「禁止」清单。
3. **去味改为「检测器给出偏离人类区间的项 → 一次定点改稿」**，并带守门项：字数、台词正式名词、流畅度底线；指标名和词表不暴露给模型，避免 r4 的刷指标副作用。
4. **写手模型对照**：同一 prompt，不同写手模型，看 AI 味指标和第一稿带内率。

### 4. 维护规矩（防止再胖回去）

- **预算的度量单位改成「每个角色每章实际加载量」**：把 agent 模板、预加载的 skill、条件 reference 的常见组合都计入，由脚本按工作流静态展开并在 CI 守卫。现有的按文件预算保留作下层约束。
- **事故补丁的置换规则**：修事故时新增一条规则，必须同时删除或合并一条，或者在预算 `why` 里写明为什么这条值得每个用户每章都付费。补丁类规则每个大版本复审一次。

### 分期

1. **v0.8.0**：基准 + v0.7.11 基线；第 1 节单章回路减负；第 3 节第 1 项精简 A/B 作为上线门槛。
2. **v0.8.x**：第 2 节概念收敛与文档重写；第 4 节新预算守卫；共享运行时打包。
3. **v0.8.x 之后**：第 3 节第 2–4 项 AI 味实验，结论按预注册口径落地。

## Alternatives considered

- **继续用现有机制：按文件压预算、把正文外移到 references**。最强理由：机制已在 CI 上跑，改动小，不用抬 `agents_version`。否：外移只改变「写在哪」，不改变「每章读多少」；三条路径预算已经顶格，实测每章仍加载约 20 万 token；子 agent 每次调用都重读，外移反而让读取次数更多。见 [热路径外移笔记](../../implemented/simplification/2026-09-07-hot-path-text-to-references.md)。
- **取消分段写作与中途 checkpoint，一次成文**。最强理由：每章少一次脚本调用和一次续写往返，写手可以整章统筹。否：#370 用实验定下分段为默认，它解决的是整章写完后反复扩写、压缩的死循环；分段本身的成本很小，而取消它的收益从未被测过。保留，只在基准里按模型观察第一稿带内率。
- **直接删规则，不先建基准**。最强理由：重复规则明显存在，逐条做 A/B 很贵。否：PR #228 曾因盲评退步撤下热路径去重；那次的评测方法虽然不可靠，但也说明删减的效果不能靠直觉判断。没有基准，删减的收益和损失都说不清。
- **全部退回主会话 solo，不用子 agent**。最强理由：省掉每次调用重读规则和冷启动；主会话本来就读过全部材料。否：主会话在单章中途已经会被压缩一次，再把写作和审查塞进去只会更早压缩；写手隔离也让「只消费批准情节点」有清晰边界。减负的方向是让子 agent 少读，而不是取消子 agent。
- **从零重写一个轻量版**。最强理由：一次甩掉历史包袱，概念可以从头设计。否：会连同真正被验证过的约束一起丢掉（hooks 门禁、追踪事务、非对称字数收口、元信息隔离），无法逐步回退，存量用户的书项目也要整体迁移。分步做、每步过基准更稳。
- **AI 味继续靠扩充禁用词和规则**。最强理由：每条禁用词都对应真实的用户投诉，加起来直观。否：tell r3/r5/r6 表明泛泛规则和范文都推不动识别率，只有可数约束和数值反馈有效；规则越多，写手 prompt 里故事素材占比越低。

## Consequences

- **收益**：
  - 按静态核算，每章加载量有望从 ~20 万 token 降到 ~6–8 万，墙钟和主会话回合数同步下降，3 章一批不再触发压缩；具体以基准实测为准。
  - 作者和维护者要理解的概念从 ~75 个降到 ~30 个量级。
  - AI 味的改进从「加规则」转为「可测、可回退的实验」。
- **代价**：
  - 基准本身要花钱：3 本书 × 3 章 × 2 个写手模型，每轮都是真实会话；预注册质量评估还要多次采样。
  - 写手模板、CLAUDE.md.tmpl、hooks 会变：要抬 `agents_version`，重新生成 OpenCode/Codex/Antigravity 等适配层，用户需重跑 `/story-setup`，UPGRADING.md 需要写迁移说明。
  - 术语退役会动到大量文档和行为锚点测试；已部署书项目的细纲字段（三档、读者契约相关字段）需要兼容读取旧格式。
  - 被删的补丁规则可能让对应的旧事故复发，只能靠基准和行为锚点兜住，兜不住的要按事故补回（届时遵守第 4 节的置换规则）。
  - 写手换用更强模型会提高单次调用单价，需要在基准里核算净成本。
