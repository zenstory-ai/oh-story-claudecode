## 否决说明（2026-11-03 追加）

本篇在分支 `feat/long-write-1.0-minimal` 上做完了实现，但没有合并，1.0 不发布。两轮预注册 Codex 对照后维护者改了方向：

- 正文（同一细纲续写七猫书第 31、32 章）：1.0 对 0.9.2 不劣，但正文更碎，短段（不到 20 字）占 59%，0.9.2 是 45%，真人 19%；维护者亲自读后认为 0.9.2 正文不差。
- 开书（设定和纲）：1.0 在作者能不能看懂上全胜 0.9.2（看不懂的词 18 对 138），但对不装 skill 的原生模型三本书两题全输，评委理由是后面的卷太薄、细纲不到场景、开篇冲突晚。

精简本身不是优势；0.9.2 的规划和写手是扎实的，问题在作者看到的写法。改为在 0.9.2 上清理，见[在 0.9.2 上清理](../../implemented/architecture/2026-11-03-long-write-0-10-cleanup.md)。1.0 分支只留作参考，其中白话模板的写法和单章白话检查被清理方案吸收。下文保留实现时的原文。

## Problem

同日的[三分重构笔记](../../rejected/architecture/2026-11-02-long-write-contract-method-example-split.md)只解决了产出缺位（没有带结局的全书梗概）和作者可见的自造词，流程复杂和体量过大都没有动。维护者决定不在现版 story-long-write 上做减法，而是从零重建一个最小版，并以 1.0 直接替换。

现状（去空白字符，doc-budget 实测）：

| 项 | 数值 |
|---|---|
| 每次调用加载量，常规／最坏：定方向 | 1.2 万／2.4 万 |
| 定设定（主会话自己做） | 2.5 万／3.2 万 |
| 出卷纲（主会话自己做） | 2.6 万／3.4 万 |
| 出细纲（主会话自己做） | 2.4 万／2.8 万 |
| 主会话直接写一章 | 2.5 万／3.4 万 |
| narrative-writer 写一章 | 2.2 万／2.8 万 |
| 原生模型同一任务 | 0 |
| 写一章的步骤数（workflow-chapter） | 13 步，含 3 个脚本、2 到 3 个子代理 |
| 开书确认点 | 4 个 |
| 长篇 skill 自带脚本 | 14 个，8782 行 |
| 部署物 | 7 个子代理、4 份规则、8 个 hook |
| 长篇文档里「必须、不得、禁止、一律、强制、不要、只能」 | 317 次 |
| doc-budget 条目 | 62 份文件加 47 条路径，几乎都顶在上限，why 字段写了 9 次「调高」 |

根子在举证责任放反了：删规则要先证明删了不退步（PR #228 的经历），加规则只要有一个真实出过的问题；评测又一直是新版对旧版、只求不劣。于是复杂度只进不出。后果是规划一部长篇的耗时远超原生模型，梗概里满是术语。

## Decision

### 举证责任反过来，分三级

story-long-write 默认不带任何机制，加回任何东西先拿证据：正确性守卫（先纲后文、文件缺失、字数带外）要一个会复现的失败用例；技法与方法文本要配对盲评或可数指标，协议预先冻结；流程步骤与子代理要墙钟加作者可见结果。

### 现在的 skill

- `SKILL.md`（约 1.6 千字）：一张「作者说 → 做什么 → 读哪份文件」的路由表，五条规矩（先有细纲再写正文；写正文要作者明确开口；一轮最多 3 章、日更默认 2 章；规划不扩大范围，上一轮在规划时「继续写」先问一句；作者说「记住……」写进 `设定/题材定位.md`「作者说过的话」），无 hook 宿主照样遵守的说明，以及只讲故事话的汇报口径。
- `references/` 四份时刻文件：`open-book.md`（开书两次确认：方向加全书梗概，大纲、角色加首批细纲；全书梗概 1500 到 3000 字、四节必写结局；全部落盘模板）、`write-chapter.md`（写一章五步：准备材料、写正文、检查、更新前情提要、汇报，含前情提要格式与一个汇报样例）、`revise.md`（补细纲、开新卷、改大纲、修改已写章）、`migrate.md`（老书迁移）。
- `references/examples/`：两篇梗概（玄幻男频、古言种田女频，取自维护者自家平台确有结局的已完结长篇，我们转述）、三段第 1 章开头原文节选（玄幻、古言种田、现言）、一份按新格式重写的 demo 书第 21 章细纲。每篇写明学什么、不学什么；开书和写前三章各只读一篇。
- 每个时刻加载的 skill 文档实测 3.4 千到 6.5 千字（旧版 2.0 万到 3.4 万），登记在 `scripts/doc-budget.json`。
- `scripts/`：`chapter_check.py`（`--before` 查细纲「这一章要让读者感到」「主角想要什么、做了什么选择」两项，缺了退出 1、不写正文，老书字段名一并认；写后统一标点、数字数、跑 `check-ai-patterns.js` 与 `check-degeneration.js`，blocking 退出 1，字数偏离细纲两成退出 2，单章问作者、日更停批；认 `<!-- 去味:跳过 -->`）、`recap_check.py`、`migrate_tracking.py`，加原有检测器副本与 `wordcount_core.py`。`tracking_commit`、`storyctl`、`build_writer_prompt`、`build_architect_brief`、`outline_view`、`author_memory_commit`、`check-outline-contract`、`check-outline-copy` 从长篇删除，别的 skill 里的副本改由导入或短篇当共享源。

### 书的状态

书目录只有 `设定/题材定位.md`（「基本信息」字段名不变）、`设定/全书梗概.md`、`设定/角色.md`（按角色分节，写章只读出场者；超过约 1 万字拆目录）、`大纲/大纲.md`（超过约 1 万字按卷拆）、`大纲/细纲_第N章.md`、`前情提要.md`。

前情提要四节固定：人物现状、未回收的伏笔、时间线、最近两章怎么结尾的；每章整份重写。`recap_check.py` 查小节齐全、三节（不含未回收的伏笔）合计不超过 3000 字、标题章号等于正文最新章；未回收的伏笔超过 25 条退出并要求列给作者问合并或放弃；与 `.story/前情提要.上一版.md` 对比，以「- 简称：」开头的条目消失而上一版没有行尾「（已回收，第 N 章）」就报错，N 不得大于最新章。通过后存快照。

### 老书与其他 skill

- 老书第一次打开时，`migrate_tracking.py` 确定性地从 `追踪/_tracking-state.json` 生成前情提要（未收伏笔一条不少、未揭示事件标「还没揭开，别提前写破」、结尾句取自最后两章正文），同时写上一版快照，`追踪/` 不动也不再更新。新版不读旧格式的派生视图。demo 书已迁移，当作一本老书保留旧细纲与 `追踪/`。
- story-import 第四阶段照旧 `tracking_commit.py init` 建追踪，再跑同一个迁移脚本生成前情提要（脚本登记为共享资产）。story-review 在书目录有 `前情提要.md` 时不再修 `追踪/` 和前情提要；consistency-checker 自己读前情提要，调用方不再传追踪修订号。story-deslop 认前情提要或老追踪判长篇。路由器把长篇的偏好交给长篇写进题材定位，通用习惯交短篇的作者记忆。
- hook 核与 Codex、OpenCode、Antigravity、ZCode 变体去掉追踪门，保留先纲后文门；会话开始、compact 前后读 `前情提要.md`，老书提示先迁移；伏笔检测改读前情提要「未回收的伏笔」。宿主说明模板、规则与 consistency-checker、narrative-writer、story-explorer 模板同步，`agents_version` 38 → 39，适配层重新生成。七个子代理都保留（审稿、短篇、导入、拆文、路由仍在用），长篇写作不再调用。
- 停用：作者记忆、文风裁决、新增物三级申报、追踪事务与派生视图、读者契约与终局储备、契约四问、排纲底稿与供给自查、对标召回、跨书召回、灵感库、题材卡与题材目录、写手与其他子代理。对标召回是第一个加回候选。
- 守卫与测试：`check-reference-gates.js` 改锚新路由与四条规矩；`current-contract.json` 的细纲必填改为两项新字段名；`scripts/test-long-write-minimal.py` 覆盖三个脚本的公开行为；`test-storyctl.py`、`test-chapter-completion-lifecycle.py` 删除，其余测试改指向新共享源。

## Alternatives considered

- **并行新 skill，旧版冻结（我最初建议）**。最强理由：老书旧格式、四个下游 skill、七宿主适配不会同时断。不采用：维护者判断同时维护两套正是现版臃肿的来路；兼容协议只有五项，清单外的耦合盘清后只有四处，同版改得完；用户基数小，破坏性升级的成本可控。
- **在现版上做减法（三分重构笔记第 3 步）**。最强理由：改动可测、守卫与适配层只需增量调整。不采用：只解决产出与术语，每时刻 2.5 万字的加载和 13 步的写章流程都在；被本篇取代。
- **保留 JSON 追踪事务与派生视图**。最强理由：它是唯一结构化权威，派生视图一致性有脚本保证，review 和 import 都接着它。不采用：7841 字的协议文档加上事务脚本是单章流程最重的一环，而长程一致性从未与「模型自维护一份有形制的前情提要」对照过；本篇把这个对照写进验收，输了再加回。
- **保留写手子代理**。最强理由：正文在干净上下文里写，主会话不被正文撑爆。不采用：没有实验证明写手胜主会话；最小版主会话本身就小；省一套七宿主适配。
- **新版双读新旧格式**。最强理由：老书零操作升级。不采用：双读路径永久留在热路径里；一次性迁移脚本一百行，旧版还能在 git 历史里找到。
- **用七猫语料原文作范例**。最强理由：人类基线最真实。不采用：版权；只做统计、前缀和分析对象。

## Consequences

- **收益**：每时刻加载从 2.0 万到 3.4 万字降到 3.4 千到 6.5 千字；写一章 5 步；开书 2 个确认点；作者第一次拿到有结局的梗概；作者会打开的文件里没有自造词；出过事的规矩有锚点守卫，前情提要有脚本守卫。
- **代价**：破坏性升级，老项目要重跑 story-setup、新开会话，追踪目录冻结；停用的功能（作者记忆、对标召回、题材卡等）在拿到证据前对长篇作者不可用，拆文产出暂时没有写作侧消费者；梗概范例只有两篇，现言、都市男频还缺一篇确有结局且内容合适的书（平台标「已完结」的书里有不少停在半路，另有几本情节大量靠性胁迫推动，都没用）。
- **正文对照（2026-11-03，预注册，小样本）**：Codex gpt-6.1-sol 续写三本七猫完结网文（玄幻男频、古言女频、现言女频）的第 31、32 章，四组同一份细纲：原生、1.0、1.0 加按场景读的技法、0.9.2，真人原章作参照。可数指标（细纲落地、演成场景、前文矛盾、越界大事、AI 句式）五组全部触顶，分不出高下；换家族（Claude）配对盲评、两次顺序一致才算胜：1.0 对 0.9.2 为 2 胜 0 负 4 平，按协议判不劣；1.0 加技法对 1.0 为 2 胜 2 负 2 平，按协议不加回；1.0 对原生 3 胜 2 负 1 平。每章耗时原生约 2.5 分钟、1.0 约 5 分钟、0.9.2 约 8.3 分钟。协议、脚本与结果在 `~/.oh-story-bench/prereg/2026-11-03-long-write-1.0-prose/`，不进仓库。
- **尚未验证**：规划可读性与长程一致性两项验收还没跑（上面的正文对照只覆盖单章正文质量与墙钟），Codex 额度待维护者定；产品 1.0 的 tag 以这三项为门槛。前情提要在百章以上的漂移、去掉写手后主会话长程是否退步，都等长程基准回答。
- **跨 skill 约定**：`前情提要.md`、`设定/全书梗概.md` 的路径是长篇写作、导入、审稿、去味与 hook 的共同约定；迁移脚本由长篇写作当共享源、导入带副本。
- **度量口径**：字数为去空白字符数，与 doc-budget 一致。
