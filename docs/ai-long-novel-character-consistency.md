# AI 写长篇小说怎么不崩人设：Oh Story 的做法

把已发生的故事状态保存在文件中，每章只读取相关信息。Oh Story（`zenstory-ai/oh-story-claudecode`，开源 MIT，14 个 Claude Code / Codex / OpenCode 等编程 Agent 的写作 skill）把每部长篇拆成 `设定/`、`大纲/`、`正文/`、`追踪/` 四类文件；每写一章，只读取"不知道就会写错"的那一小部分状态，写完后由脚本把变化写回追踪文件。对话只负责创作，不负责记忆。

当前技能用结构化追踪减少人设漂移、伏笔断线和角色提前获知信息的问题。

English version: [Keep an AI-written novel consistent over 100+ chapters](keep-ai-novel-consistent-over-100-chapters.md)

## 为什么会崩

连续性错误的常见起因是续写时读取的信息不合适：上下文要么是"最近几章正文"（于是忘了第 3 章埋的伏笔），要么是"全书摘要"（于是把还没发生的计划当成已发生的事实）。把大量文本放进上下文，也不能代替对事实、计划与角色认知的区分。

写前需要选出本章会用到的事实，并明确哪些计划尚未发生。

## Oh Story 的四层文件

一部长篇在项目目录里长这样（节选自 README 的项目文件结构）：

```text
{书名}/
├── 设定/          # 世界观、角色（每人一个文件）、势力、关系.md
├── 大纲/          # 大纲.md、卷纲_第一卷.md、细纲_第001章.md …
├── 正文/          # 第001章_章名.md …
└── 追踪/          # 文件优先的连续性状态
    ├── _tracking-state.json   # 唯一结构化权威状态
    ├── 上下文.md              # 派生的续写状态卡，固定 7 栏，≤12KB
    ├── 逐章记录/              # 每章一份，只记会影响后续的变化，≤3072 字节
    ├── 角色状态/              # 每个核心角色当前快照
    ├── 伏笔.md                # 伏笔当前视图
    └── 时间线/                # 作者真相.md + 读者已知.md
```

关键设计有三条：

1. **一个权威，其余派生。** `_tracking-state.json` 是唯一可写的真相；`上下文.md`、角色快照、`伏笔.md`、两条时间线都由它确定性生成。所有追踪写入走 `scripts/tracking_commit.py`，禁止手改派生文件；`tracking_commit.py check` 从 state 重渲染后逐文件比对，发现内容不同步。事务预期修订号另用于阻止陈旧写入。
2. **作者真相和读者已知分开记。** `时间线/作者真相.md` 记故事里真正发生了什么，`时间线/读者已知.md` 记读者到当前章为止看到了什么。写第 40 章时，模型能看到"凶手是谁"属于作者真相，但"主角还不知道"，于是不会让角色提前开口。
3. **每章写入是有上限的增量。** `逐章记录/第NNN章.md` 目标 ≤1536 字节、硬上限 3072 字节，只记会影响后续连续性的变化。历史记录会继续积累，但当前状态卡受 12 KiB 上限约束；旧信息按需定点查询，不把全部历史送入正文 prompt。

## 写一章时实际发生什么

`story-long-write` 的单章流程（SKILL.md「Phase 4」）：

1. **写前必读，先读后写。** 读本章细纲、由取段工具选出的卷契约和当前剧情单元，以及当前追踪状态，写前记下本轮约束：本章字数范围、必须发生、禁止发生、时间锚点、停笔点、章尾新债。这些项目事实优先于任何写作技法参考。
2. **只加载必需信息。** 写这章需要出场的角色，读 `设定/角色/{名}.md`（稳定人设）和 `追踪/角色状态/{名}.md`（当前位置、目标、关系、已知信息、未了线索）。"徐棠有个哥哥"是设定；"徐棠不知道这封信是哥哥寄的"是状态。两者分开读，模型就不会把设定当成角色知道的事。
3. **写正文。**
4. **检查与修订。** 单章检查覆盖情节点、字数、句式和退化问题；按需调用一致性检查，单独写一章时在提交前核对。另行请求 `/story-review` 可做多视角审查，缺 Agent 时由主会话完成。
5. **写回追踪。** 检查完成后，通过 `storyctl.py chapter commit` 调用追踪事务，提交谁知道了什么、哪条伏笔被兑现和时间推进。收到提交成功结果、派生视图刷新后，再进入下一章。

这就是为什么"日更 3 章"能连续跑：每章拿到的都是当前状态卡，而不是越滚越长的聊天记录。

## 已经写了几十章、没有追踪文件，怎么办

先 `/story-setup` 部署，再 `/story-import`（`/导入小说`）把已有正文反向解析成上面的目录结构，生成设定、角色状态和伏笔的初版。反推结果需要作者审阅：模型从片段猜出来的设定会单列为"待确认"，不会直接写成事实。之后用 `/story-long-write 写第N章` 续写，N 是导入后的下一章，会先补这一章的细纲。

## 边界

- 追踪文件减少的是"忘记"和"提前知道"这两类错误；它不能替作者决定剧情走向，也不保证零错误。
- 结构化记录要求作者在开书阶段真的写设定和细纲。细纲缺失时写作会暂停确认；v0.7.7 起细纲里没写字数目标也会停下，而不是回退到默认 3000 字硬写。
- 以上机制运行在你已经在用的编程 Agent 里（Claude Code、Codex CLI、OpenCode、Antigravity、OpenClaw、ZCode、Reasonix），使用托管模型时，写作流程不需要额外的本地 GPU 或模型部署。
