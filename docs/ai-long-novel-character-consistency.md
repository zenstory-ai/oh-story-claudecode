# AI 写长篇小说怎么不崩人设：Oh Story 的做法

把已发生的故事状态保存在文件中，每章只读取相关信息。Oh Story（`zenstory-ai/oh-story-claudecode`，开源 MIT，14 个 Claude Code / Codex / OpenCode 等编程 Agent 的写作 skill）把每部长篇拆成 `设定/`、`大纲/`、`正文/`、`追踪/` 四类文件；每写一章，只读取「不知道就会写错」的那一小部分状态，写完后由脚本把变化写回追踪文件。对话只负责创作，不负责记账。

这套工具用结构化追踪文件，减少人设走样、伏笔断线和角色未卜先知的问题。

English version: [Keep an AI-written novel consistent over 100+ chapters](keep-ai-novel-consistent-over-100-chapters.md)

## 为什么会崩

长篇连载容易前后矛盾，往往是因为续写时喂给模型的信息不对：要么只给「最近几章正文」（结果忘了第 3 章埋的伏笔），要么只给「全书梗概」（结果把还没发生的后续计划当成了已经发生的事）。光往上下文里塞更多字数，并不能帮模型分清「已经发生的事实」「还没落地的计划」和「角色当下知道什么」。

动笔前需要先筛出本章用得上的事实，并标清哪些安排还没发生。

## Oh Story 的四层文件

一部长篇在项目目录里长这样（节选自 README 的项目文件结构）：

```text
{书名}/
├── 设定/          # 世界观、角色（每人一个文件）、势力、关系.md
├── 大纲/          # 大纲.md、卷纲_第一卷.md、细纲_第001章.md …
├── 正文/          # 第001章_章名.md …
└── 追踪/          # 文件优先的连载状态
    ├── _tracking-state.json   # 唯一底账（原始状态数据）
    ├── 上下文.md              # 自动生成的续写状态卡，固定 7 栏，≤12KB
    ├── 逐章记录/              # 每章一份，只记会影响后续的变化，≤3072 字节
    ├── 角色状态/              # 每个核心角色当前状态卡
    ├── 伏笔.md                # 伏笔当前清单
    └── 时间线/                # 作者真相.md + 读者已知.md
```

关键设计有三条：

1. **一份底账，其余自动生成。** `_tracking-state.json` 是唯一可写的总账；`上下文.md`、角色状态卡、`伏笔.md` 和两条时间线都由它自动生成。所有追踪更新都通过 `scripts/tracking_commit.py` 写入，不要手改自动生成的文件；`tracking_commit.py check` 会从底账重新生成并逐份比对，发现手改就会报错。提交时还会核对版本号，防止旧数据覆盖新进度。
2. **作者真相和读者已知分开记。** `时间线/作者真相.md` 记故事里真正发生了什么，`时间线/读者已知.md` 记读者到当前章为止看到了什么。写第 40 章时，模型能看到「凶手是谁」属于作者真相，但「主角还不知道」，于是不会让角色提前说漏嘴。
3. **每章只记有上限的增量变化。** `逐章记录/第NNN章.md` 目标 ≤1536 字节、硬上限 3072 字节，只记会影响后续连载的变化。历史记录会继续积累，但当前状态卡控制在 12 KiB 以内；旧信息按需定点查询，不把全部历史塞进正文提示词。

## 写一章时实际发生什么

`story-long-write` 的单章流程（SKILL.md「Phase 4」）：

1. **写前必读，先读后写。** 读本章细纲、由取段工具选出的本卷主线和当前剧情段，以及当前追踪状态，动笔前先记下本章约束：字数范围、必须发生的事、不能提前发生的事、时间锚点、停笔位置、章尾新留的钩子。这些本书设定和细纲要求优先于任何通用写作技法。
2. **只加载必需信息。** 写这章需要出场的角色，读 `设定/角色/{名}.md`（稳定人设）和 `追踪/角色状态/{名}.md`（当前位置、目标、关系、已知信息、未了线索）。「徐棠有个哥哥」是设定；「徐棠不知道这封信是哥哥寄的」是状态。两者分开读，模型就不会把背景设定当成角色自己已经知道的事。
3. **写正文。**
4. **检查与修订。** 单章检查覆盖情节点、字数、句式和重复退化问题；按需调用一致性检查，单独写一章时在提交前核对。另行运行 `/story-review` 可做多视角审稿，没有子代理时由主会话完成。
5. **写回追踪。** 检查完成后，通过 `storyctl.py chapter commit` 更新追踪底账，记下谁新知道了什么、哪条伏笔已回收、故事时间走到了哪。确认提交成功、追踪文件刷新后，再进入下一章。

这就是为什么「日更 3 章」能连续跑：每章拿到的都是最新状态卡，而不是越滚越长的聊天记录。

## 已经写了几十章、没有追踪文件，怎么办

先 `/story-setup` 部署，再 `/story-import`（`/导入小说`）把已有正文反向解析成上面的目录结构，生成设定、角色状态和伏笔的初版。反推结果需要作者审阅：模型从片段猜出来的设定会单列为"待确认"，不会直接写成事实。之后用 `/story-long-write 写第N章` 续写，N 是导入后的下一章，会先补这一章的细纲。

## 边界

- 追踪文件减少的是"忘记"和"提前知道"这两类错误；它不能替作者决定剧情走向，也不保证零错误。
- 结构化记录要求作者在开书阶段真的写设定和细纲。细纲缺失时写作会暂停确认；v0.7.7 起细纲里没写字数目标也会停下，而不是回退到默认 3000 字硬写。
- 以上机制运行在你已经在用的编程 Agent 里（Claude Code、Codex CLI、OpenCode、Antigravity、OpenClaw、ZCode、Reasonix），使用托管模型时，写作流程不需要额外的本地 GPU 或模型部署。
