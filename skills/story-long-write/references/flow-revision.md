# 回炉大修与症状诊断（flow-revision）

> 谁读：主会话修改、回炉、重写已写章节时整份读；同时按需读 `flow-drafting.md`「正文笔法与竖屏网感」与本书 `references/genre-styles/{流派}.md`。

只改细纲不进本文件，走 `flow-outline.md`。作者只说读者反应或模糊感受（「中间拖了」「不爽」「太闷」）、没点名哪章时，先走下方「症状诊断」找出问题章请作者确认，再进 Step 1。

---

## 症状诊断（作者只说感受时先用）

| 作者或读者反馈 | 优先排查 | 常见病因 | 改法与对应手册 |
|---|---|---|---|
| **开头留不住人 / 闷** | 第 1–3 章 | 纯景物开篇、前 400 字无冲突、金手指拖到 3 章后、章末没断章 | 按 `flow-drafting.md` 黄金三章铁律 + 本书流派包开篇重写；结构错先按 `flow-outline.md` 改纲 |
| **像传统小说 / 文学腔重 / 看着累** | 段落与标点 | 大段 >80 字叙述墙、长连词复句、对话 <15%、满屏句号没情绪张力 | 对照本书流派包或对标 `文风.md` 的原文切片重拆短段（≤40字为主），补对话交锋与直白情绪 |
| **拖、水、不知道在干嘛** | 期待链与松紧 | 旧爽点兑现后没立新期待；无信息过场拉长；兑现拖太久 | 把拖久的兑现前移，无信息过场并章；兑现前先埋下一条麻烦/奖励钩（`flow-outline.md`） |
| **爽不起来 /「就这？」** | 铺垫与围观层 | 对手逼格没立住、主角胜得太憋屈、缺少内行拆解与有利害者改口 | 按 `flow-drafting.md` 装逼打脸四步补足前置轻视、干脆碾压、分层震惊与实利落袋 |
| **「又是这一套」/ 腻了** | 相邻剧情段 | 连续两段重复同场景、同对手或同破局方式 | 回 `flow-opening-plan.md` 换场景、换对手层级或开发金手指新用法 |
| **主角憋屈 / 毒 / 圣母** | 四个排纲问题 | 功劳被外援/机构抢走；主角犯低级蠢错；核心资产白交没交换 | 回 `flow-opening-plan.md` 四个排纲问题修纲，把关键抉择和实利拿回主角手里 |
| **换地图后崩了** | 换图前 3 章 | 旧关系旧期待全部清空，变成从零开始的新书 | 回 `flow-opening-plan.md`「对标迁移与换地图」，带入旧仇、老熟人或上级势力线 |
| **变味 / 串台** | 流派边界 | 写了邻近题材的节奏或雷区（如爽文写成长段苦大仇深留白） | 回到本书 `genre-styles/{流派}.md` 核对定位、声线与雷区红线 |
| **AI 味重 / 机械重复** | 表达与节奏 | 论文腔、空洞升华、机械微动作刷屏、提纲照搬 | 局部按 `flow-drafting.md` 六条黑名单改；整章精修走 `/story-deslop` |

先用白话给作者诊断（最多 1–2 个主因 + 建议先改第几章 + 一句话改法），作者点头再动手。

## 大修流程

### Step 1：定章与改动范围

1. 定位 `正文/第{X}章_*.md`（按章号或章名关键词查找，找不到就问）。
2. 判断范围：点到具体段落/场面（「那场打脸」「结尾对话」）→ **局部修改**；说「重写」「回炉」→ **整章重写**。拿不准时用白话选项问：
   - 1. 只改点到的地方，其余不动（推荐）
   - 2. 按原细纲整章重写
   - 3. 先改这章细纲，再按新细纲重写（选 3 先走 `flow-outline.md`）

### Step 2：按范围加载上下文

- **必读**：待改章全文、`大纲/细纲_第{X}章.md`、`tracking_commit.js check`（取 `state_revision`）与 `追踪/上下文.md`（缺 state 时停下，请先走 `/story-import` 补追踪）。
- **局部修改**：前一章只看末尾几段（第 1 章无）、后一章存在时只看开头几段；只读涉及角色卡与 `追踪/角色状态/{名}.md`。
- **整章重写**：前后两章全文 + 细纲点名角色与设定；第 1 章看 `设定/题材定位.md` 与本书流派包原文切片。

### Step 3：备份、改写与检测

1. **备份与计字**：复制原稿为 `正文/第{X}章_章名_原稿_{YYYYMMDD}.md`；跑 `node {skill 根}/scripts/storyctl.js wordcount measure --file {正文文件}` 记原字数。
2. **改写**：已部署 `narrative-writer` 时按 `agent-calls.md`「大修改写」派发；否则主会话按 `flow-drafting.md` 笔法与流派包切片自改。局部修改不动范围外文字，不擅自加细纲外剧情。
3. **检测收口**：跑 `node {skill 根}/scripts/storyctl.js chapter check --project {书目录} --chapter {X} --fix-punctuation --plain`。硬伤清零，`review_required` 改净或提交时附 `--ack <rule-id>:<理由>`；字数出带欠字不补、超字净删一次，仍超请作者选；差异超过 30% 或 800 字时汇报中写明对比。
4. 核对人物、伏笔与前后章衔接无冲突；外部事实不明时先查证再提交。

### Step 4：追踪级联更新与提交

用一次 `mode=revision` 事务更新（报错才读 `tracking-protocol.md`）：

1. 跑 `node {skill 根}/scripts/tracking_commit.js draft --project {书目录} --chapter {X}` 预填草稿；对照新正文保留有效项、修正被推翻项，不清空重写。
2. 逐项重算受影响的伏笔当前值（到最新已写章 M）、时间线事件（删掉的标 `action=delete`）和核心角色截至 M 章的完整快照。若 X ≤ `imported_through_chapter`，事务自动生成覆盖记录。
3. 跑 `node {skill 根}/scripts/storyctl.js chapter commit --project {书目录} --chapter {X} --input {书目录}/.story/work/第{XXX}章/tracking.json`（字数带外先给作者 1. 按现长度收下 / 2. 再调整 / 3. 退回原稿 三个选项，选 1 用 `accept-current-length` 或 `--ack length:<理由>`，不到目标一半坚持才加 `--force`）。
4. 跑 `tracking_commit.js check --project {书目录}` 确认状态干净，并扫一遍后续章看是否受本次改动影响。

### Step 5：向作者汇报（白话，不带代码块围栏）

<!-- author-report -->
```md
第{X}章《{章名}》改好了，原稿留着，想退回随时说：
- {改了什么：原来怎样 → 现在怎样}
{篇幅差超 30% 或 800 字时补一句字数变化；没超就删}
{后面章受影响时：「第{X+1}章《{章名}》里{某设定/情节}还按旧说法写，要一起改吗？1. 一起改（推荐）2. 先不动」；不受影响写「后面的章不受影响」}
```

连续改多章时逐章走 Step 1–5。
